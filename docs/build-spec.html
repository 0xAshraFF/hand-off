Four rules that decide arguments

When a build decision is contested, these settle it.

  1. The model classifies, the code selects. No language model ever names a model that ends up in front of a user. It returns job types from a fixed enum; our scorer reads the catalog and picks.
  2. Nothing is a ruling. Every recommendation ships with a cheaper option, a pricier one, and a stated limitation. Copy never sounds final.
  3. Reduce the asking, never the answer. Fewer questions is always a fair trade. A thinner recommendation is not.
  4. Prefer the single key. When two models score close, the one reachable on an OpenRouter key wins, because the other one costs the user a signup they did not plan for.

Language, which lives in two places

Conflating these is the mistake to avoid. They are different settings with different jobs, and for many users they will hold different values — someone in Dhaka may well read the interface in English while building a bot that must answer in Bengali.

Interface language

  • Detected from navigator.languages on first load. Never a blocking question.
  • A switcher sits in the header at all times, persisted in localStorage (wrapped in try/catch — it throws in private windows).
  • Purely cosmetic. It changes no recommendation.
  • Sets <html lang>, and dir="rtl" for Arabic, Urdu, Hebrew and Farsi.

Project language

  • Asked at step 4. Defaults to the interface language, and is changeable.
  • Multi-select — most real projects are bilingual, usually English plus one.
  • It is a recommendation input: filters out models that score badly on the chosen languages, and reweights the rest by their multilingual score.

This is the part that earns its keepMultilingual ability is already in the Artificial Analysis feed as a Multilingual Index, so this costs one extra column in the catalog and one filter in the scorer. The payoff is large: the best model for a Bengali or Arabic support bot is often not the one that tops the English leaderboard, and the models that are strong in Chinese — GLM, Qwen — are exactly the cheap ones people have not heard of. Language turns out to be one of the better routes to the discovery the product is for.

RTL is real engineering, not a checkboxArabic and Urdu need dir="rtl", logical CSS properties throughout (margin-inline-start, never margin-left), mirrored icons for directional arrows, and numbers that stay left-to-right inside right-to-left text. If Arabic is not in the launch set, build with logical properties anyway so adding it later is a translation job rather than a rewrite.

Suggested launch set

English, Bengali, Hindi, Indonesian, Spanish, Portuguese, Arabic, Chinese. Chosen for where enthusiast builders are numerous and English-language tooling serves them least. Prices stay in USD — that is what providers bill in — with an optional converted figure beside them, and all numbers formatted through Intl.NumberFormat with the interface locale.

The screens

Screen 01

Copy our prompt

Purpose

Hand the user a prompt that makes their own chatbot decompose their project for free.

On screen

  • The prompt in a bordered block, in the interface language, plus one Copy button.
  • One line saying what to do with it: take it to Claude or ChatGPT, bring back what it gives you.
  • A "I already have a task list" link that skips straight to screen 02.

The prompt itself

Worded to force bullets rather than prose, because bullets parse and prose does not:

Give me a handoff for my project, task by task.
Plain bulleted list, one line per task, 12 tasks maximum.
No preamble, no explanation, no code.

Stored

Nothing.

Away · not our screen

Their chatbot

The user leaves. This is intended. Their assistant already holds the project context, runs on their subscription, and does the decomposition better than we could from a form. We lose them for thirty seconds and gain the whole hard part for nothing.

Expect some to come back with prose despite the instruction. Screen 02 must survive that.

Screen 02

Paste it in

Purpose

Turn whatever came back into a clean, visible, editable task list before anything is sent.

Behaviour

  • One textarea. On paste, parse client-side into bullets — split on newlines, strip leading -, *, • and 1. markers, drop empty lines.
  • Render the result as an editable list: each task a row, each row deletable and editable, with an Add task control.
  • Cap at 12 tasks. Extras are trimmed and the trim is stated, never silent.
  • Cap each task at 200 characters and the whole payload at 800 words.
  • If parsing yields one blob (they pasted prose), show it as a single editable task and say so plainly: "That looks like one big task. Split it up, or send it as is."

Stored

The task array, in session state. Persisted to the account only if they later choose to save.

Why the editable list matters

It is the moment the user sees exactly what is about to be sent, and can remove anything they did not mean to share. That is worth more for trust than any privacy copy.

Screen 03

What can you spend?

On screen

  • A slider, plus a per month / per run toggle.
  • Label phrased in money and plain words, never tokens. At zero: "Free tiers and models you run yourself."
  • Four preset chips so nobody has to drag: $0, $5, $20, no limit.

Stored

budget_amount, budget_period.

Screen 04

What language must it work in?

On screen

  • Multi-select chips, pre-selected with the interface language.
  • A short line explaining why it is being asked: "Some models are much better in some languages than others."
  • Skippable — skipping means English only.

Stored

project_languages: string[] as BCP-47 codes.

Screen 05

Your recommendations

Layout

The user's own task wording down the left — verbatim, never rewritten, so they recognise their project. Three columns across: Cheaper, Recommended, Stronger. Recommended carries the accent; the others stay neutral.

Each cell

  • Model name and provider.
  • Estimated cost for that task at that model.
  • A single-key badge when it is reachable on OpenRouter; an explicit "needs its own account" flag when it is not.
  • Tapping it opens: why this one, what it is not for, and two near-misses.

Above the table

A running total against the budget, with a plain-words verdict — fits, comfortably under, over by $12. Swapping any cell recomputes it live.

States

StateWhat shows
NormalThree columns, totals, verdict.
Nothing fits the budgetThe cheapest possible build, with the gap stated: "The cheapest way to do this is about $Y." Never an empty screen.
Budget far exceeds needRecommended stays cheap, with a line saying so. Never spend their money to look thorough.

Screen 06

Your handoff document

Assembled in code from the selections. No second model call. Default tab is prose for pasting into a chat; AGENTS.md and models.json sit behind it. Copy and Download, and the copy confirmation says "Copied — paste it back where you got the task list."

The one call, as a contract

Request. The user's task text is untrusted input — it came out of one model and is heading into another.

POST /api/recommend
{
  "tasks": ["Set up user login", "Parse uploaded PDFs", ...],
  "budget": { "amount": 20, "period": "month" },
  "languages": ["en", "bn"]
}

The model is called once, with a strict response schema. Note what it cannot return:

{
  "classifications": [
    {
      "task_index": 0,
      "job_type": "auth_and_glue",      // enum, closed set
      "volume": "low",                   // low | medium | high
      "confidence": 0.91,
      "rationale": "Standard login flow, little reasoning needed."
    }
  ]
}

// job_type is one of exactly:
//   ui_work · debugging · bulk_processing · reasoning
//   vision · long_context · auth_and_glue · media_generation
//
// There is no field for a model name. Validate on arrival and
// reject anything off-schema rather than passing it through.

Our scorer then runs, with no model involved:

for each classification:
    candidates = catalog
        .filter(fits_budget_share)
        .filter(supports(languages))       // multilingual index floor
        .filter(supports(modalities_for(job_type)))
    scored = candidates.map(score_for(job_type, weights))
    pick     = best(scored)
    cheaper  = best(scored.filter(cost < pick.cost))
    stronger = best(scored.filter(score > pick.score))
    // tie-break, always: available_on_openrouter wins

Cost and cachingAbout 1,500 tokens in, 400 out — roughly $0.0005 a call on a cheap flash model. The system prompt and schema are ~1,200 of those tokens and identical every time, so prefix caching takes most of the input to near zero. Store the analyzer as a catalog row and let the scorer choose it for the job "classify short text into a fixed schema, cheaply", rather than pinning a model ID in code.

What the handoff document contains

  1. One line of context — what they are building, from their own task list.
  2. The routing table — task, model, and one sentence on why.
  3. Getting set up — "Create one OpenRouter key at openrouter.ai; it reaches every model below except those marked." Then the exceptions, each with where to sign up.
  4. Rules for the assistant — use the named model for each task, do not substitute silently, say so if a model is unavailable.
  5. Their original task list, quoted and fenced, clearly marked as the user's own words.

The fencing is not optionalThis document is designed to be pasted into someone's AI assistant, which makes it an injection vehicle if user text is ever interpolated into an instruction position. Task text appears only inside a fenced, labelled block. Instructions are generated from our template and the enum'd classifications — never from user strings.

Written in the interface language, with model IDs, API terms and URLs left verbatim in Latin script. Offer an "English version" toggle: some users will prefer to hand their assistant English regardless, and that preference should be theirs.

When things go wrong

FailureWhat the user sees
Classifier times out or returns malformed JSONRetry once. Then fall back to keyword-matched job types and label the result "rough — we could not read every task clearly". Never an error page: a rough recommendation beats none.
Catalog sync failed last nightServe the last good catalog and show its date. Stale by two days is fine and honest; silently stale is not.
A recommended model was withdrawnThe nightly sync marks it unavailable; the scorer skips it. A saved plan holding it shows "no longer available" and offers the current equivalent.
Pasted text is not a task listShown as one editable task with a plain-words nudge to split it. Still proceeds.
Free-tier quota exhaustedFalls back to the deterministic path, never a wall. Says what was lost: "Using your task list as written, without the extra read."
Interface language has no translation for a stringFalls back to English for that string only, never a raw key.

Not in the first version

  • Hugging Face and GGUF. Needs a third data source, quantization sizing and a VRAM question. Best tier, slowest to get right — do not let it block launch.
  • Accounts and saved plans. The whole flow works logged out. Add accounts when there is something worth saving.
  • Image and video. No public benchmark backs it; the useful answer is a workflow and a quantization, not a model and a price.
  • Community and trends. Needs volume before it shows anything true. An empty trends page is worse than no trends page.
